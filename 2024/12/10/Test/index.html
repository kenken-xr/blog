Android dvm 的进程和Linux 的进程, 应用程序的进程是否为同一个概念

  1. Linux 进程

在 Linux 系统中，进程是资源分配和调度的基本单位。一个进程包含了程序执行所需的各种资源，如内存空间、文件描述符、CPU 时间片等。每个进程都有自己独立的地址空间，进程之间通过系统调用（如管道、共享内存、消息队列等方式）进行通信和数据共享。例如，当在 Linux 终端运行一个程序时，系统会为这个程序创建一个进程，这个进程会有自己的进程 ID（PID），并且会在系统的进程管理机制下运行。

  1. Android DVM（Dalvik Virtual Machine）进程

在早期的 Android 系统中，DVM 用于执行 Android 应用程序。DVM 进程是运行在 Linux 内核之上的一种特殊进程。它为每个 Android 应用程序创建一个独立的运行环境，这个环境包括了自己的虚拟机实例、内存空间等。DVM 进程和 Linux 进程有密切的关系，因为 DVM 本身是运行在 Linux 系统之上的，它利用了 Linux 的进程管理机制来创建和管理 DVM 进程。例如，当安装并启动一个 Android 应用时，系统会为这个应用创建一个 DVM 进程，DVM 会加载应用的字节码并执行。

  1. 应用程序进程（Android）

在 Android 中，应用程序进程是指运行一个 Android 应用的进程。从用户角度看，当打开一个应用，这个应用就在一个独立的进程中运行。这个进程实际上是由 DVM（早期）或 ART（Android Runtime，现在主流）来执行应用的代码。应用程序进程和 Linux 进程紧密相关，它是在 Linux 内核基础上构建的，并且遵循 Linux 的进程管理规则，同时它也和 DVM/ART 进程相关，因为 DVM/ART 负责在这个进程中执行应用程序的逻辑。

Binder是如何做到一次拷贝的

商家 – 快递柜 – 用户

内存被操作系统划分成两块:用户空间和内核空间，用户空间是用户程序代码运行的地方，内核空间是内核代码运行的地方。为了安全，它们是隔离的，即使用户的程序崩溃了，内核也不受影响。

Binder 通过使用内存映射（mmap）技术实现一次拷贝。在 Linux 内核中，mmap 系统调用可以将一个文件或者设备映射到进程的虚拟地址空间。

Binder 驱动利用这个原理，在发送进程和接收进程的用户空间以及内核空间之间建立映射关系。

当发送进程要传递数据给接收进程时，数据被存储在发送进程的用户空间缓冲区。Binder 驱动将这个缓冲区在内核空间进行映射，同时也将接收进程的用户空间的一块区域与内核空间的相同区域进行映射。这样，数据就可以直接从发送进程的用户空间通过内核空间传递到接收进程的用户空间，而不需要额外的数据拷贝。

MMAP的原理讲解

Linux通过将一个虚拟内存区域与一个磁盘上的对象关联起来，以初始化这个虚拟内存区域的内容，这个过程称为内存映射(memory mapping)。

把内核空间的地址和服务端进程中的一块虚拟内存同时映射到Binder的驱动

对文件进行mmap，会在进程的虚拟内存分配地址空间，创建映射关系。

实现这样的映射关系后，就可以采用指针的方式读写操作这一段内存，而系统会自动回写到对应的文件磁盘上

  1. 在用户空间调用mmap后，会在当前进程的虚拟空间中分配一段区域并使用vm_area_struct(vma)结构记录这个区域。
  2. 通过文件描述符链接到内核中的文件结构体，每个文件结构体维护着打开文件的相关信息;
  3. 通过文件结构体file*定位到了文件，建立页表，将文件对应的物理地址和vma映射关联;
  4. 进程的读或写操作访问虚拟地址空间这一段映射地址但是目前只建立了地址映射，真正的硬盘数据还没有拷贝到内存中，因此引发缺页异常，触发将文件内容拷贝到与vma(虚拟内存)关联的物理内存，

mmap 是一种内存映射文件的方法，它允许进程将文件的内容直接映射到进程的虚拟地址空间。

其基本原理是，当进程调用 mmap 系统调用时，内核会为进程的虚拟地址空间分配一段连续的地址范围，这段地址范围与文件的物理存储区域建立关联。

例如，一个文件存储在磁盘上，通过 mmap，该文件的内容可以被 “看作” 是存储在进程的内存空间中。当进程访问这段内存区域时，就好像访问普通的内存一样，但实际上是由内核通过页表等机制将内存访问转换为对文件的读取操作。这种方式可以提高文件访问的效率，尤其是在处理大型文件或者频繁读写文件的场景中。

  1. 生成的 Java 类结构
    1. 当编译 AIDL 文件时，会生成相应的 Java 类。这些 Java 类主要包括一个接口（继承自android.os.IInterface）和一个内部抽象类（继承自android.os.Binder）作为存根（Stub）。
    2. 接口： 这个接口与 AIDL 文件中定义的接口相同，用于客户端调用。它包含了 AIDL 文件中定义的所有方法，这些方法的参数和返回值类型与 AIDL 文件中的定义一致。
    3. 存根类（Stub）： 存根类实现了前面提到的接口，并且重写了onTransact方法。onTransact方法是 Binder 通信的核心方法之一，它用于接收从客户端通过 Binder 驱动传来的事务。在这个方法中，存根类会根据事务中的方法编号，调用相应的实际服务方法，并将结果返回给客户端。同时，还会生成一个静态的asInterface方法，用于客户端获取服务端对象的代理对象。这个方法会根据传入的Binder对象判断是在同一个进程还是不同进程，如果是不同进程，则返回代理对象，否则返回服务端实际对象。

四大组件底层的通信机制

  • Activity

    • Activity 之间的通信可以通过 Intent 来实现部分功能。但在底层，当一个 Activity 启动另一个 Activity 时，并不是直接进行启动操作，而是通过向系统的 Activity Manager Service（AMS）发送请求来实现。这个过程中，应用进程和 AMS 之间的通信是基于 Binder 机制。AMS 通过 Binder 机制与各个 Activity 所在的进程进行通信。
    • 例如，当启动一个新的 Activity 时，当前进程会通过 Binder 向 AMS 发送请求，AMS 会检查目标 Activity 的相关信息（如是否存在、是否需要创建新的进程等），然后通过 Binder 通知目标 Activity 所在的进程进行创建和启动操作。

  • Service

    • Service 主要用于在后台执行长时间运行的操作。它与其他组件的通信也是基于 Binder 机制。当一个组件（如 Activity）要绑定一个 Service 时，会通过 Binder 机制获取 Service 的代理对象，然后通过这个代理对象与 Service 进行通信。系统向 Service 所在的进程发送启动请求，Service 所在的进程会根据请求创建和启动 Service。

  • Broadcast Receiver

    • Broadcast Receiver 主要用于在不同的应用之间共享数据，用于接收系统或者应用发出的广播消息。
    • 当一个应用发送广播时，它会通过系统的广播机制发送消息。这个消息首先会被发送到 AMS，在这个过程中，应用进程和 AMS 之间的通信是通过 Binder 机制实现的。应用进程会将广播消息（包括广播的类型、携带的数据等）封装成一个事务，通过 Binder 驱动发送给 AMS。

  • Content Provider

    • Content Provider 用于在不同的应用之间共享数据。它通过 Binder 机制向外提供数据访问接口。当一个应用（客户端）要访问另一个应用（服务端）中的 Content Provider 数据时，会通过 Binder 获取 Content Provider 的代理对象，然后通过这个代理对象执行查询、插入、更新、删除等操作。
    • 例如，一个应用中的数据库数据通过 Content Provider 暴露给其他应用。Content Provider 会实现一个继承自android.content.ContentProvider的类，这个类会通过 Binder 机制返回一个ContentResolver的代理对象给客户端应用。客户端应用通过这个代理对象（ContentResolver）执行查询、插入、更新、删除等操作来访问 Content Provider 中的数据。

  • 底层传输机制限制

    • Intent 主要是通过 Binder 机制来传递数据。而 Binder 机制在传递数据时有一定的限制，它虽然有高效的数据拷贝方式，但对于大数据来说，可能会导致性能问题或者超出 Binder 的传输能力。因为 Binder 的缓冲区是有限的，大数据可能无法完整地放入这个缓冲区。

  • 安全和效率考虑

    • 从安全角度看，传递大数据可能会增加安全风险。例如，恶意应用可能会利用 Intent 传递大量数据来攻击系统或者其他应用。从效率角度考虑，传递大数据会占用较多的系统资源，包括内存和 CPU 时间，这会影响整个系统的性能。因此，为了保证系统的安全性和高效性，Intent 通常不适合传递大数据。如果需要传递大数据，可以考虑使用其他方式，如文件共享、Content Provider 等。

Handler 内存泄漏原因

1. 非静态内部类持有外部类引用

  • Handler 通常作为内部类存在于 Activity 或者其他组件中。非静态内部类会默认持有外部类的引用，当 Handler 发送的消息还在消息队列中等待处理，并且这个消息包含了对 Handler 的引用（通常是隐式的），那么这个 Handler 又持有外部类（如 Activity）的引用。

  • 如果 Activity 在应该被销毁时，由于消息队列中的消息没有处理完，导致 Activity 无法被垃圾回收器回收，就会发生内存泄漏。例如，在一个 Activity 中创建了一个 Handler 用于延迟执行一个任务，当 Activity 要销毁时，这个延迟消息还在消息队列中，那么 Activity 就无法被正常回收。

与其他内部类的对比

普通内部类和匿名内部类的引用问题

  • 其他内部类如果也持有外部类的引用，在某些情况下也可能导致类似的问题。但是，Handler 在消息处理的场景下更容易出现这种情况。对于普通的内部类，如果没有涉及到类似长时间等待处理的消息机制，只要内部类的生命周期和外部类合理地同步，就不太容易出现内存泄漏。

  • 例如，一个普通的内部类只是在外部类的某个方法中被短暂使用，当这个方法执行完，内部类的引用如果没有被其他地方持有，就会被垃圾回收。而 Handler 由于其消息处理机制的特点，消息可能在消息队列中停留较长时间，从而增加了内存泄漏的风险。

ViewRootImpl是UI刷新的核心类，所有UI相关动作，包括触摸、触屏事件、响应事件、按键事件都是有ViewRootImpl来完成。

  • Activity 与 Window 关联建立：

    • 在 Activity 的 attach 方法中，创建 PhoneWindow，并通过 setWindowManager 操作建立与 Window 的联系。

  • Window 与 View 关联建立：

    • 绘制流程起始于 WindowManagerImpl.addView ()，在其内部调用 WindowManagerGlobal.addView ()，此过程中创建 ViewRootImpl。
    • 通过 ViewRootImpl.setView ()，借助 WindowSession 进行 IPC 调用，将 View 添加到 Window 上。
    • 例如，当 Activity 从不可见变为可见（如从后台恢复到前台），ActivityThread 的 handleResumeActivity 方法执行 addView 操作，实现 View 与 Window 的关联，使 View 能在 Window 对应的屏幕区域显示。

三者分工：

  • Activity： 负责界面交互与业务逻辑处理，管理 Window 生命周期，协调 View 的创建、显示与更新。例如，用户点击按钮等交互操作触发 Activity 中的事件处理方法，依据业务逻辑决定是否更新 View 显示内容。

  • Window： 作为屏幕显示区域的抽象概念，是 View 的载体，提供显示区域与属性设置（如窗口样式、透明度），负责将 View 正确展示在屏幕上并处理与系统窗口相关操作（如与 WMS 交互）。

我们说丢帧是因为主线程做了耗时操作，为什么主线程做了耗时操作就会引起丢帧？

因为耗时操作会影响下一帧的绘制。

Android 系统一般要求在 16ms 内完成一帧的绘制（以达到 60FPS 的帧率），若主线程被耗时操作占用，导致绘制下一帧的时间超过 16ms，就会出现掉帧现象。

在主线程中进行复杂的网络请求或大量数据处理，会延迟 View 的绘制操作，使画面卡顿，影响用户体验。

连续两次setTextView到底会触发几次UI重绘呢？

连续两次 setTextView 只会触发一次 UI 重绘。因为 UI 必须至少等待 16ms 的间隔才会绘制下一帧。

当连续快速设置 TextView 的文本内容时，由于第二次设置可能在 16ms 内，系统会将这两次设置合并为一次重绘操作，等待合适时机进行绘制，以避免过度频繁的绘制操作浪费系统资源。

为什么Android APP的帧率一般是60FPS?

以电影为例，动画至少达到 24FPS 才能保证画面流畅度，低于此值肉眼会感觉卡顿。

在手机上，为增加丝滑度，将帧率调整到 60FPS，对应的每帧绘制时间约为 16ms（1000/60）。

Android 系统通过 VSYNC 信号保证每 16ms 最多绘制一帧，这样可以使画面在人眼视觉上更加流畅和连贯，提供更好的用户体验。

android 中的动画有哪几类，它们的特点和区别是什么？

  1. 逐帧动画（Frame - by - Frame Animation）
    1. 逐帧动画是通过一系列连续的图片来创建动画效果。就像传统的动画制作一样，将每一个动作分解成多个帧，每一帧都是一个单独的图像。例如，制作一个人物行走的逐帧动画，可能需要绘制人物在不同行走姿势的多个图片，然后按顺序播放这些图片来形成动画。
    2. 它是基于时间顺序依次显示预先定义好的一系列帧图像。这些帧图像可以是通过手工绘制、使用图像编辑软件制作或者从视频中提取等方式得到。在 Android 中，可以通过在AnimationDrawable中定义一系列的drawable资源作为帧，然后在代码中设置动画的播放时间、循环次数等参数来实现逐帧动画。
    3. 与其他动画类型相比，逐帧动画的制作过程相对复杂，因为需要准备多个帧图像。而且由于每一帧都是完整的图像，文件大小可能较大，占用较多的内存资源。它的优点是可以实现非常复杂和精细的动画效果，比如具有丰富细节的角色动画等。
  2. 补间动画（Tween Animation）
    1. 补间动画是通过定义起始状态和结束状态，由系统自动计算中间的过渡状态来生成动画。例如，要实现一个视图从一个位置移动到另一个位置的动画，只需要定义起始位置和结束位置，系统会自动计算并生成在这两个位置之间过渡的动画效果。
    2. 它基于数学函数和插值算法来计算中间状态。在 Android 中，有四种基本的补间动画类型：位移（Translate）、缩放（Scale）、旋转（Rotate）和透明度（Alpha）。可以通过在 XML 文件或者代码中定义这些动画的参数，如起始值、结束值、动画持续时间、插值器（用于控制动画的速度变化）等，来实现不同的动画效果。
    3. 相较于逐帧动画，补间动画的文件大小和内存占用通常较小，因为它不需要存储大量的帧图像。它的制作相对简单，只需要定义关键的起始和结束状态即可。但是，补间动画只是改变了视图的显示效果，并没有真正改变视图的属性，例如一个通过补间动画移动位置的视图，其实际的布局位置并没有改变。
  3. 属性动画（Property Animation）
    1. 属性动画可以对任何对象的属性进行动画操作，并且能够真正地改变对象的属性值。例如，可以对一个自定义对象的某个自定义属性（如颜色、形状等）进行动画处理，使这个属性随着时间发生变化。
    2. 通过设置动画的目标对象、目标属性、动画持续时间、值的变化范围等参数，利用时间插值器和类型估值器来计算在动画过程中属性值的变化。在 Android 中，主要使用ValueAnimator和ObjectAnimator来实现属性动画。ValueAnimator用于计算属性值的变化，ObjectAnimator是ValueAnimator的子类，它可以直接将动画应用到目标对象的属性上。
    3. 与补间动画不同，属性动画可以真正改变对象的属性，而不仅仅是视觉上的效果。与逐帧动画相比，它不需要大量的帧图像，并且在灵活性上更高，可以对各种对象的各种属性进行动画处理。
