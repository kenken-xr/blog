  • 群消息没有⽀持漫游，消息⽆唯⼀字段。

解决方案

⽤⼤⼩、性能、安全性综合最优⽅案设计跨平台统⼀的全新客户端DB，

  • 控⼤⼩：好友的uid为字符串，做主key会导致DB过⼤，为每个uid分配⼀个64位的本地index，从1开始。
  • 提性能：流⽔和消息⼀个事务⼊DB（防丢失），凑够100条(可配置)才提交到搜索表，提交成功后删除流⽔。
  • 业务完整性： ⽤户搜索时，主动提交⼀次流⽔表的存量消息，防⽌搜索不到。
  • 搜索性能：采⽤SQLite最新的FTS5搜索引擎，搜索性能⼤幅提升。
  • 分类查询：做好了各种索引，能快速分类查找（如图⽚/⽂件/表情/链接等）， ⽼QQ基本分类⽆索引。
  • 安全加密：改造SQLite，全库加密

把客户端和后台通信的ID升级成了字符串，不再是4字节的QQ号。不仅在账号安全上更有利，更重要的是为后续我们彻底突破42亿的账号数量限制打下了基础。

  • 账号数量存在上限 -> 突破42亿限制
  • 易被便利存在安全隐患 -> 账号不会被遍历
  • 回收账号影响用户体验 -> 牵引完成容器化和架构升级

消息相关核⼼模块的优化

以聊天窗⼜（AIO）为例，基于全新数据流架构 + 数据预加载 + UI逻辑并⾏化的设计思路，完成单向数据流驱动与异步加载渲染，系统资源全⼒供给AIO消息列表，最终性能指标提升明显， AIO内查看、跳转、滑动消息，顺畅丝滑。核⼼技术优化⽅案：

  1. 采⽤基于单向数据流的MVI（Model-View-Intent）架构，实现业务解耦
  2. 预加载和异步渲染，实现消息⽆缝滑动
  3. 消息加载并⾏化，减少⾸屏和滑动时的加载时间
  4. 消息动态加载、释放，优化内存占⽤
  5. 200+业务组件懒加载，实现数据分层和按需加载

==MVI==

它建立在单一的、不可变的状态（State）上，所有的状态变化都是通过一个循环流（Cycle）来管理的。

Model：代表应用的状态。在MVI中，状态是不可变的，任何状态的变化都会产生一个新的状态对象。
View：负责展示状态（Model）并将用户的操作转换为Intent。
Intent：不是Android中的Intent，而是用户意图的表示，它告诉应用需要做什么。这些意图会被转换为状态改变。

MVI架构的核心思想在于，所有的数据流动都应该是单向的和可预测的。

MVI的优点
可预测性：由于状态是不可变的，且所有状态变化都是单向和循环的，这使得系统的行为更加可预测。
简化调试：单一的状态和单向数据流让时间旅行调试成为可能，我们可以很容易地追踪状态的变化。
易于测试：每个组件都有明确的职责，且状态的不可变性使得编写测试变得更简单。

MVI的缺点
状态管理：在复杂的应用中，管理单一的状态可能会变得困难。
样板代码：应用MVI可能需要写更多的样板代码来定义状态、意图等。

使用场景
MVI特别适合于需要强大响应性和状态管理的应用，如实时聊天、表单验证和复杂交互的应用程序

消息列表单项进⾏了区域划分，所有的节点项都继承于同一个Item，BaseChatItem，并重写⾥⾯areItemsTheSame、areContentsTheSame、 getChangePayload这⼏个接⼝，来让Diff差分判断的时候确定指定节点数据是否需要进⾏更新以及相应的⼀个更新区域。 在列表数据发⽣更新的时候，RecyclerView借助DiffUtil进⾏差量更新操作，其采⽤Myer算法来计算需要增删改的节点和相应节点区域，并将增量数据变化通知给RecyclerView来达到增量更新的⽬的。

由于越细粒度的位置划分虽然能更精确的控制处理特定区域的更新，但同时也会带来更⼤规模的类离散问题。所以综合考虑消息列表更新位置和相应的UI控件结构（不同控件可可能对应同⼀个位置区域） ，主要将节点项区域拆分成了如图多个不同的 Part 区域，每个Part 除了提供默认的通⽤项处理操作（⽐如设置默认值，复⽤重置） ，同时提供注⼊逻辑，以⽀持业务根据⾃身需要对对应区域变动进⾏处理。

注： ==Myer算法==解决的是最⻓公共⼦序列问题（LCS）的等价问题——最⼩编辑脚本（SES）问题，是时间复杂度为为O(ND)的diff算法，其基于动态规划实现。它通过将每个字符与其相应的参考字符进⾏⽐较来确定哪些字符需要被插⼊、删除或替换。该算法⾸先初始化⼀个⼆维数组，该数组包含两个字符串的⻓度以及两个字符串中每个位置的最佳编辑操作。然后，该算法通过⽐较两个字符串的每⼀对字符来更新这个⼆维数组，并确定哪些字符需要被插⼊、删除或替换，最终⽣成⼀系列的编辑操作，通过通过该操作能将第⼀个字符串转为第⼆个字符串。

就以diff两个字符串为例，其中N为两个字符串⻓度之和， D为两个字符串的差异部分的总⻓度。如示例图，对于序列X=ABCABBA及序列Y=CBABAC得到相应的编辑图，其连通左上到右下顶点的最短路径的解即为该问题的最优解。

UI层面——ListAdapter

基于跨平台提供的数据， UI层⾯在做数据展示的时候，最好也需要有⼀个全量数据更新的⽅案。于是，直接采⽤ListAdapter就成了⼀个⾮常好的选择：

  • ⾃动计算差异： ListAdapter使⽤ DiffUtil⾃动计算列表数据的差异，并根据这些差异进⾏最⼩化的更新。这可以提⾼列表的性能，特别是当列表数据量⼤的时候。
  • 简化代码： ListAdapter处理了许多繁琐的更新列表数据的⼯作，如计算差异、调⽤正确的notify⽅法等。简化代码，更加专注在数据处理， ⽽不是在Diff逻辑上。
  • 提⾼⽤户体验： 提供平滑的动画效果，为后续Item动画的开发提供了巨⼤的便利，当列表数据发⽣变化时， ⽤户可以清楚地看到哪些项被添加、删除或移动。
  • 线程安全：ubmitList⽅法可以在任何线程上调⽤，它会⾃动在主线程上处理列表数据的更新。这可以避免在主线程上进⾏耗时的差异计算，从⽽避免UI卡顿。

ListAdapter里面维护着线程池并且还会为我们将视图修改操作移到主线程，这样我们就可以很方便的使用DiffUtil

实际上,DiffUtil算法还是耗时间的,如果数据更多,估计时间也会随之增多,所以,官方推荐开启个异步线程来处理计算,之后分发操作再切换UI线程进行数据的更新操作

之后的数据增删改查都需要调用adapter提供的submitList()方法即可

优化

首屏优化

在UI层之前，任意⼀步出现⾼耗时，都有可能会导致⾸次进⼊到⼿Q的时候，看到⼀个空⽩的⻚⾯。因此降低NT、数据处理层这两个环节的耗时就变成了⼗分重要的事情。

降低NT⾸屏回调的耗时——快照

要降低NTSDK的耗时是不太可控的， 其主要原因是NTSDK在启动时， NTSDK会加载各个模块的DB，并且在各个模块中进⾏数据处理，这部分的操作都是异步的，并不在主线程，因此⽆法保证在启动过程中，数据处理完成⼀定早于消息列表⾸屏绘制。因此，消息列表快照就成为了⼀个不错的选择：

可以让上层的⾸屏数据不再依赖于NTSDK初始化以及⾸次抛数据

  • 在NTSDK回调上层数据变化的时候， UI层⾯采⽤⼀定的策略，定时去获取消息列表Top N数据的⼆进制，并且持久化到⽂件中。
  • 在启动的时候，将快照数据从⽂件中读出，并且解码，作为⾸屏数据进⾏展示。

在数据的刷新的时候，触发⼀个任务，对数据进⾏持久化。

降低⾸屏数据处理的耗时——⾸屏数据分段处理

通过快照处理之后，我们发现数据处理耗时也是⼀个瓶颈。设计之初，为了降低在UI线程做的任务，我们将很多事情都移动到了异步线程，提前去获取数据， ⽐如：
头像：我们会在数据处理环节中，提前将头像获取⼀次，保证完成⽹络下线、解码。
摘要：提前把各种Element进⾏拼接、转换，保证在到了UI线程只需要调⽤setText。
昵称以及各种关系链标记：提前把各种关系链铭牌进⾏提醒获取，保证不需要阻塞UI线程进⾏获取。

为了提⾼⾸屏数据上屏的效率，我们对⾸屏数据进⾏了裁剪，即：

  • ⾸屏上屏的时候，仅只⽤Top N数据，第⼀次仅处理少部分的数量，同时部分业务数据不进⾏处理（⽐如各种互动标识、表情Icon） ，保证优先刷新到屏幕中。
  • 保证第⼆次优先刷新，保证⾸屏的全量数据进⾏刷新，保证数据的完整性。

降低数据传递的耗时——Flow改Callback

⾸次在框架设计上，我们在数据仓库连接VM、 VM连接UI上都采⽤Flow， 原因是Flow有以下的⼀些优势：简化异步编程： Flow是Kotlin中的⼀种处理异步数据流的⽅式，同步的⽅式编写异步代码， ⼤⼤简化了异步编程。

⽀持协程： Flow是协程友好的，它可以在协程中使⽤，并且⽀持协程的取消和异常处理机制。
⽀持操作符： Flow提供了⼀系列的操作符，如map、 filter、 reduce等，可以更⽅便地处理数据流。
⽀持主动数据丢弃： ⼀些特定的Flow可以帮我们drop old，减少数据处理的压⼒。

但是，采⽤Flow也带来了⼀些问题：
启动阶段线程负载⾼，协程调度缓慢。
协程切换虽然花销少，但是仍然存在协程切换。

线程切换开销：Flow操作可能涉及协程的线程切换，这会带来一定的开销。

背压策略：Flow的背压策略可能会导致数据处理延迟，尤其是在数据生成速度和消费速度不匹配时。处理数据流中生产者和消费者速率不匹配问题的一种机制。在流处理系统中，生产者是生成数据的源头，消费者是消费数据的终端。如果生产者生成数据的速度超过了消费者处理数据的速度，就会出现数据积压的问题，这时就需要背压策略来控制和协调数据流。

​ 实时数据处理：在实时数据处理场景中，比如传感器数据、点击流数据等，使用 buffer 或 conflate 可以有效处理数据流。

​ 批量数据处理：在批量数据处理场景中，比如大数据分析，使用 buffer 可以暂存数据，等待批量处理。

​ 用户界面更新：在用户界面更新场景中，比如滚动列表更新，使用 conflate 或 latest 可以避免频繁的UI更新，提升性能。

调度器问题：使用不适当的调度器也可能导致延迟。例如，在主线程上执行耗时操作会阻塞 UI 更新，导致延迟。

冷启动延迟：Flow是冷流，在订阅时才开始执行。第一次订阅可能会有一些初始化开销，导致延迟。

硬件和系统资源：设备的硬件性能、系统资源利用率等也会影响执行效率。

我们在测试过程中，发现在同⼀个线程下，采⽤Flow传递数据，仍然会有偶现的150ms-200ms的延迟（启动阶段） 。最终，我们将数据仓库连接VM部分切换成了Callback。

滑动优化

降低UI线程耗时——UI预创建

在滑动的过程中，有相当⼀部分卡顿是发⽣在了⾸次滑动的时候，其主要原因是在⾸次滑动的时候，有⼀定概率会触发绑定新的ViewHolder， ⽽RecyclerView中没有缓存，因此需要触发⼀次CreateViewHolder。 ⽽LayoutInflate的过程中是相对⽐较重的，耗时不稳定。 ⽽⼀旦出现⾼耗时， 给⽤户的体验就是滑动过程中出现了掉帧。

  • 将Item的UI从Xml转换为Code：即采⽤代码编写UI，减少触发LayoutInflate的耗时。
  • 启动⼀个异步线程，在⾸屏UI绘制完成之后，对部分可以服⽤的UI进⾏预创建，保证在滑动的时候，即使触发了CreateViewHolder，也可以以⼀个⽐较低的耗时，返回⼀个Item ViewHolder。

⽆锁化更新

上层消息处理为了⽀持异步化处理，同时保证结果的顺序性，采⽤了系统提供的HandlerThread +Handler 的⽅式。 HandlerThread 保证异步顺序的原理是实际是通过 MessageQueue 来实现的，其是Android 框架层⾥⾯的⼀个核⼼类，主要基于双向链表实现队列式的消息处理。

阻塞式并发处理

数据处理这⾥，基于上屏速度的考虑，对于列表数据项的处理采⽤当前线程+异步多线程来提⾼加速效率（实测数据多的情况下， ⾮⾸次能提⾼约30%） 。这⾥有⼀个问题，这⼀块需要保证顺序，那么如何对异步线程进⾏阻塞管控？对⽐信号量、读写锁的⽅式，这⾥考虑主要是对于线程数和消息处理项数的处理，通过利⽤CountDownLatch + AtomaticInteger 结合使⽤，即保证异步并发处理，同时在任务处理完继续顺序执⾏接下来的逻辑。

性能优化

代码及静态资源

加载如此庞大的代码会占用大量内存。因此，仍然需要进行代码瘦身、静态资源优化、分包和按需加载等优化措施。

  • 代码瘦身。对于第三方包或 SDK，它们往往包含了完备的 Web 兼容性及能力，而有些并不是必需的。进行定制裁剪或独立实现，以减少代码的加载。
  • 不完全按照每个页面（窗口）以及模块复用次数来进行制订，按照场景模块来进行细粒度的定制。
    • 以打开一个窗口到进入使用场景为例：
    • 1）窗口池中预启动的窗口页面只加载必须执行的基础代码；
    • 2）当打开具体窗口时加载对应的路由后页面入口代码；
    • 3）当具体使用不同功能时动态加载，如点击搜索、打开表情面板、转发消息激活好友选择器的时候才会分别加载对应功能模块代码。
  • 静态资源（如 SVG、base64 图像）在加载时也会占用不少内存，按需加载的策略：只在可见时加载，不可见时主动销毁和回收。
  • 提升执行效率和代码保护的，将 JS 代码转成了字节码。跳过了源码编译，直接将字节码交给 V8 执行，但在程序报错还原堆栈等运行时步骤中，V8 仍然会引用源码字符串。为了去掉这份源码，我们使用和源码等长的空格来占位，但通过 devtool 检查发现这些空格字符串仍会占用不少内存空间。最终，我们采取修改和移除 V8 对源码字符串引用的方式，彻底解决了源码字符串的内存占用问题。

图片资源

  • 一张分辨率为 4000 x 2750 的图片，结合设备屏幕像素和聊天区设计尺寸，只需渲染宽度为 567 像素的分辨率图像即可清晰展示。如果以宽度为 4000 像素的分辨率渲染，理论上两者位图所占用的内存大小差距可达 50 倍，并且还会因为渲染带来性能损失。在聊天消息列表中的大部分图片仅仅起到预览作用，缩略图渲染就满足了需要。而仅仅在用户真正打开图片查看器放大查看时，才会需要用原图渲染。

根据屏幕设备信息和计算展示区域所需实际渲染分辨率，当原图分辨率超出计算所需值，则先调用压缩服务进行图片压缩，生成渲染所需分辨率的缩略图，并在聊天区域进行渲染上屏。在这个策略的优化下，一般聊天图片场景测试下来，使用缩略图比原图约有 30M ~ 50M 的内存优化。

DOM 元素数量

严格的控制DOM 元素使用数量，采用”所见即占用“的 渲染策略。只有视口所见的内容才会渲染对应 DOM 元素。其他所有组件在不渲染展示时，均会移除组件及其 DOM 元素来避免其内存开销。

我们将普通分页列表替换为虚拟滚动列表，并且对列表滚动 buffer 进行极限压缩甚至是 0 buffer 。由于不再一味采取空间换时间，没有 buffer 的情况下必然面对列表滑动性能挑战，因此也需不断优化各类 item 组件渲染性能。

精简组件 DOM 层级，移除非核心组件 keep-alive (重新优化渲染性能) 等方式，大账号使用下整体的 DOM 数量从 13000 减少到控制在平均 4000 以内，这部分优化减少约 20M 内存。

渲染图层

渲染图层方面，在渲染时满足某些特殊条件的渲染层，会被浏览器自动提升为合成层，达到提升渲染性能的目的。但是每个合成层都占用额外的内存，应当去掉过量且不必要的合成层来控制图层带来的内存占用。当然结合渲染性能考量，对于高频且列表等核心模块，是可以单独提升合成层。

在桌面端 QQ 中通过超级调色盘可以为进行色彩换肤，在这个场景中全局各模块有不少单独提升的合成层来实现毛玻璃、渐变和纹理效果。另外还有许多不经意间被提升的隐式合成层。通过对不必要的合成层进行移除与合并，整体也优化了约 9.3M 内存。

结构化消息

QQ 支持丰富的消息类型，从简单的文本、图文消息，到复杂的 lottie 表情、下图所示的业务可定制的结构化消息等。我们知道 JavaScript 是单线程的，这些消息同时上屏的时候可能会出现过长的上屏任务而导致 UI 卡顿，给到用户的感受就是切换消息列表卡顿，消息上屏慢等糟糕的体验。

使用了 JavaScript 事件机制结合 WebWorker 来实现消息异步上屏，并使用 OffscreenCanvas + Worker 池绘制来提升渲染性能。

为了在 Canvas 中实现 CSS 的 Flex 布局效果，我们采用了跨平台的布局解决方案，将 Yoga 编译成 WebAssembly 运行在 WebWorker 中。Yoga 官方编译采用的是 asm.js 的方案， 这种方案不支持动态分配内存，可以看到它默认分配了一个较高的内存，达到了 128M。

为了优化 WebAssembly 的内存占用，我们调整了编译方式，将 Yoga 编译成独立的 wasm 文件，这种方式相比 asm.js 支持动态内存分配。同时结合聊天窗口的消息卸载策略，经过不断的测试调优，在既要保证初始内存较少又要尽可能避免内存爆发式增长带来的性能损耗的前提下，我们把 WebAssembly 的初始内存分配优化到 2M，再加上对象共享、享元模式等策略，WebWorker 的内存占用有了非常可观的优化。

复杂的聊天消息虽然是必不可少的功能，但是实际的消息量还是远少于普通的图文消息，因此在保证用户体验的前提下，在合适的条件下适时销毁 WebWorker 是一个合理的策略，而随着 WebWorker 被销毁这个线程所占用的内存也能被完全释放。

Lottie 及动画方案选型

超级表情采用 Lottie 动画技术方案，有高清高帧率高质量特点，但同时也为我们带来了渲染的高成本。为了保证 Lottie 的高帧率和减少 CPU 占用，我们缓存了 Lottie 渲染器生成的动画帧，内存消耗成为了首要问题。

对其进行定量分析，超级表情 Lottie 资源继承自手机 QQ，尺寸是 512 × 512，动画帧以 int8 数组存储，所以一帧动画为 512 × 512 × 4 / 1024 bit= 1024 Kb = 1Mb，一个普通大小的超级表情，例如庆祝表情，有 160 帧动画，依据缓存 9/10 帧动画的策略，庆祝表情会占用 144Mb 内存，虽然是可回收的，但也无疑是巨大的内存消耗。关注到 Lottie 渲染的内存消耗后，我们主要从以下 2 步入手：

  • 缓存的动画帧尺寸：桌面端 lottie 渲染大小为 120 × 120，考虑到需要保持 Lottie 动画的高质量，缓存的动画帧尺寸调整为实际尺寸大小的两倍，即 240 × 240，降低内存消耗 72%。经设计确认，清淅度上也没有明显的差异；
  • 缓存策略：缓存 9/10 的动画帧减少到缓存 3/4，降低内存消耗 35%，而且调整之后帧率还能得到保障；

旧策略对于渲染过且暂时不用的 Lottie 表情，会 buffer 它的第一帧，总共 31 个 Lottie 表情：2.3k * 31 = 7M（最多），经评估之后，我们暂时也拿掉了该策略。

聊天列表与消息

列表在静态与滚动过程中，维持消息组件的数量多少决很大程度决定整个app内存占用。消息数据从服务端拉取后会存储在本地 DB，根据策略会将当前会话的消息数据缓存在内存中。

随着滚动加载，消息缓存占用的内存也越多，所以也有一定动态阈值的策略，丢弃滚动方向相反的旧消息，从而将内存控制在可接受范围。如果用户重新操作又需要加载时，这请求底层向本地磁盘 DB 重新拉取。

最早版本中对消息上屏没有丢弃策略，内存增量没有很好控制。于是采用分页列表，屏内保持固定几页消息（约 30 ~ 50 条消息，视屏幕尺寸决定），超过范围的消息进行丢弃，列表高度由屏内消息直接撑起，用户通过触顶或触底进行上下一页消息的加载。

但这带来些点问题：一方面随着触顶触底，滚动条频繁跳动的体验并不好；另一方面列表高度由不定高的组件渲染消息来维持，不得不始终保留 30 ~ 50 条消息以撑起滚动高度，不可见消息的那部分便造成内存的浪费。

  • 使用虚拟列表维持计算高度后，列表不再依赖保持真实消息内容的渲染，理论上我们可以将可视区域以外的消息实例全部销毁，仅保留用户可见的消息，最大程度地压缩消息实例数量，指保留很少的 buffer 消息实例。在实际滚动中由于消息实例在滚动过程被不断创建和销毁，占用主线程，影响 UI 绘制和用户输入。因此我们还做了：
    • 1.对创建销毁做一定聚合，批量处理消息上屏。
    • 精简优化单条组件的渲染性能。
    • 不同滚动方向调整上下不同 buffer 大小 等等措施。
    • 会话切换和窗口聚失焦最小化等操作时对不再使用的消息资源内存进行主动回收。

消灭内存泄漏

我们知道 V8 有自己的垃圾回收机制，虽然它在 GC（垃圾回收）方面有着其各种策略，并做了各种优化从而尽可能的确保垃圾得以回收，但我们仍应当避免任何可能导致无法回收的代码操作。常见的例子包括：

  • 未移除的监听器和定时器：在监听事件处理函数其中引用的不被释放导致的泄漏。
  • 游离 DOM 未释放：移出 document 后游离 DOM 仍存在引用导致无法释放。较多发生于框架的组件销毁时，相关监听未取消导致组件没有释放的情况。
  • 监控 / 打点导致的泄漏：在使用 Performance.mark 打点监控时，产生 PerformanceMark 对象，在用完之后没有手动清除，也会导致内存泄漏。
  • console.error 导致的泄漏：控制台持有被打印对象始终不释放，导致应用的泄漏。
  • 其他不当的闭包及隐式的全局变量。

以上是桌面 QQ 在早期遇到的常见问题

为了避免频繁采集上报内存指标所带来的的性能消耗，设定了一定时间的采集间隔，同时针对使用场景的采集做了抽样。并将渲染进程 pid 映射寻找窗口名，只在若干次采集后再做聚合计算，通过 SDK 上报到 prometheus + grafana 的指标观测平台。

防劣化与自动化测试

建设一个防劣化平台，主要通过自动化的端对端 (e2e) 测试来持续监控项目集成后的性能变化。

  • 定时对主干上集成构建的程序进自动化 e2e 测试；
  • 除了对功能的冒烟测试外，针对重点关注的性能指标，构造了对应的帐号和环境，编辑特定的用例，用于采集性能指标；
  • 通过将采集和采样的指标上报到防劣化的监控平台，来监控项目集成后的性能变化，如会话切换响应时间、内存占用、CPU 使用率等；
  • 监控平台提供按版本和时间的指标曲线、对比，方便查看和分析性能变化情况。同时打通企业微信机器人，对性能指标情况进行实时推送告警；
  • 根据告警信息对应的版本信息和代码记录，排查情况，闭环问题。

⽆限列表

滑动区域判断更新

⽆限列表在整个列表中的数据区域类似⼀个滑动窗⼝，窗⼝区域有⼀定⼤⼩变动限制， ⽽可视区域则是尽可能保持在滑动窗⼝中间，这样能保持⽤户在进⾏上下滑的时候，在各处基本都能保证顺畅滑动。
当前消息列表界⾯的列表使⽤的Android的系统控件RecyclerView，通过监听RecyclerView.OnScrollListener，并根据列表位移值进⾏滚动⽅向判定，以及借助LinearLayoutManager.findFirstVisibleItemPosition()和LinearLayoutManager.findLastVisibleItemPosition() 判断当前滚动的位置，当触及触发位置时，则进⾏对应⽅向数据的加载

上划dy > 0 ：加载底部数据

下滑dy < 0 ：加载顶部数据

翻⻚过程UI的动态更新

数据刷新主要有两点：

  1. 上层数据层维护⼀份基本数据，当NTSDK通知数据更新时，对新增变更数据进⾏增量数据处理，同时与原数据进⾏合并形成新的数据集合，这时获取到UI需要更新的数据集合。
  2. 列表使⽤数据层处理之后的数据集合进⾏UI更新， UI更新借助 Android 系统提供的⼯具DiffUtil进⾏列表的增量Diff，然后对列表执⾏notifyItemInserted、 notifyItemChanged、 notifyItemRemoved等操作，配合处理元素上的Payload，从⽽实现增量的对特定节点项或者特定项的某些区域进⾏更新。

跳转特定项 | 未读项处理

由于⽆限列表分⻚的数据不可能是全量的， ⽆法直接在缓存查找之后进⾏跳转，所以结构设计的考虑点如何处理可能异步数据刷新带来的定位问题结合性能和容错的问题，主要将结构分成上下两块：

上⾯⼀部分先⾛当前缓存⻚⾯的查找，如果找不到，则不需要通过NT再去查找。

下⾯⼀块是在查找不到的情况，通过NT查找，并处理查找数据定位情况， 重点在于数据状态缓存，然后在发⽣数据刷新的时候根据该缓存状态再去跳转

无限列表功能的设计与

优化为仅缓存可视区部分的会话详细信息，以及影响列表排序的关键字段

列表中的会话是在不停变动的。为保证吞吐以及灵活性，SDK 提供的多为异步接口。基于上述原因，在发生临界会话跳变或删除时，就变得难以处理：从会话 z 处触发向后拉取（拉取更旧的会话）；由于是异步接口，在执行拉取动作前，会话 z 收到了一条新的消息，新位置位于会话 a 前；此时，底层执行拉取动作，返回给上层的列表并不符合预期。

随着会话增多，内存占用仍会增加

按 UI 绝对位置进行拉取

用户从列表绝对位置为 200 处向后拉取； 绝对位置 200 处所在的会话收到新消息，位置发生变动，此时有新的会话占据了列表 200 的位置；底层执行拉取动作，返回给上层是更新后的 201-400 处的会话。相较于方案一，该方案不需要关心处在拉取位置处的具体会话，反而是直接返回拉取位置处新的会话即可。
缺点：随着会话的增多，额外的内存占用仍会参加

使用 DB 排序取代内存排序，

用户从缓存中的第 200 个会话来时拉取；底层缓存中的列表发生变化；底层执行拉取动作，从当前缓存的第 200 个会话开始拉取，
我们认为结果是符合预期的。
缺点：依赖 DB 排序，需要新增并维护排序字段，方案相对复杂，且相比于内存排序，耗时较长。
